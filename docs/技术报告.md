# 技术报告：个人所得税联动计算器

> 版本：v0.6.0（已发布）。政策复核日期：2026-10-07。
> 本文档面向评审与使用者，阐述三项核心工程设计：**年度版本化规则集**、**年终奖临界区间的机制性推导**、
> **结果数值的依据联动（ref 溯源）**。全部结论可由仓库内的代码、规则包与内置基准复现：
> `incometax benchmark` 一条命令即可跑完全部自洽性检查（本机实测 1184 项全部达标，单次不足 1 秒）。

## 一、年度版本化规则集：把"政策随时间变化"做成一等公民

### 1.1 问题

个人所得税规则不是常量，而是随年度变化的政策集合。以本项目覆盖的 2019-2026 纳税年度为例，
至少存在三类年度差异：

| 差异点 | 2019-2021 | 2022 | 2023-2026 |
|---|---|---|---|
| 3 岁以下婴幼儿照护 | 无（六项扣除） | 每孩每月 1000 元（设立） | 每孩每月 2000 元 |
| 子女教育 | 每孩每月 1000 元 | 同左 | 每孩每月 2000 元 |
| 赡养老人 | 独生 2000 元/月；非独生分摊总额 2000、每人 1000 | 同左 | 独生 3000 元/月；非独生分摊总额 3000、每人 1500 |
| 年终奖单独计税 | 财税〔2018〕164号，至 2021-12-31 | 公告2021年第42号，至 2023-12-31 | 公告2023年第30号，至 2027-12-31 |

如果把年度差异写成 `if year >= 2023:` 之类的代码分支，就会把政策事实固化进程序逻辑：
政策一更新就要改代码、重新测试、重新发版，且**代码里出现政策数值本身就违反可溯源性**
（某个 2000 是从哪份文件哪一条来的？）。

### 1.2 设计：规则包为唯一事实源

本项目的做法是把**全部政策事实外置**为年度规则包 `data/rules/ruleset-YYYY.json`（schema v1）：

- 每个数值条目形如 `{"value": …, "ref": {"source": "S2023", "clause": "第二条"}, "status": "已核对"}`——
  **数值 + 出处文号/条款 + 核对状态**三元组；
- 引擎代码中**不出现任何政策数值字面量**：税率级距、速算扣除数、扣除标准、临界端点全部查表得到。
  这条纪律由 `tests/test_zero_policy_literals.py` 强制：它把 2019-2026 全部规则包的数值条目与两张税率表
  收编为禁用 token（≥100 的整数、对应小数与原样税率串），对 `engine/ + benchmark/ + gui/ + cli.py`
  做词边界扫描，连文档字符串与注释都扫（宁严勿松）。年度数字 2019-2026 本身也是规则包 token，故源码一律不写年份。

切换年度 = 换一份 JSON。GUI 的年度下拉框、CLI 的 `--year`、汇算与预扣引擎走的是同一条查表通路，
不存在"某年度特有的代码分支"。

### 1.3 status 门控：把"无出处数值不得生效"红线下沉为代码

规则包区分 `已核对` / `待核对` 两态。加载器 `load_ruleset()` 允许**结构加载**（供预览），
但引擎入口 `effective_ruleset()` 是单点门控：只要存在待核对条目，就抛 `RulesetNotEffective`
并列出全部待核对条目路径，**拒绝进入任何计算**。

- 门控覆盖面 = 含 `value` 键的数值条目 + 两张税率表逐行（`status_report()` 界定）；
  来源登记 `sources[]` 与说明性 `desc/ref_qd` 节点不参与门控（它们不进入计算结论）；
- 引擎入口（monthly/settlement/bonus/deductions/compare/derive）**内部再次调用** `effective_ruleset()`，
  即"前端忘了门控"也不会漏放——这是防御性冗余，不是重复实现；
- CLI `rules` 命令可预览待核对状态但不拦截，把"差哪些条目"如实告诉用户，而不是静默拒算。

### 1.4 复核元数据：核对日期与下次复核进入规则包

`schema v1` 在本轮新增两类**附加元数据**（不改变 `schema_version`，不影响计算语义）：

- `sources[].reviewed_at`：该来源的核对日期（`YYYY-MM-DD`）；
- 顶层 `review`：`reviewed_at` / `next_review` / `basis_year` / `carry_forward_years` / `scope_note`。

schema 校验日期格式、`next_review` 严格晚于 `reviewed_at`、`carry_forward_years` 为整数列表。8 份规则包的
当前口径为：`reviewed_at=2026-10-07`、`next_review=2027-01-31`；2019-2021 以 2019 原文为依据、2022 单独核对、
2023-2026 以 2023 原文为依据且 `scope_note` 明确写出 **"2024-2026 沿用 2023 标准，未取得逐年度新文件"**。
CLI `rules`、CLI `calc` 来源图例与 GUI 依据面板均从规则包读取并展示该日期，源码不写死年份。

年终奖单独计税（财政部 税务总局公告2023年第30号）执行至 **2027-12-31**；该日期是下次复核必须确认的政策边界。

### 1.5 冻结与可复现

规则包是**生成器产物**，不是手写文件：`tools/gen_rulesets.py` 从年度模板 + 差异点参数化生成全部 8 份。
`tests/test_gen_rulesets.py::test_regeneration_byte_identical` 逐字节守门——改规则必须改生成器并整目录重生成，
杜绝"手改一份 JSON 悄悄漂移"。真值库对账、位级守门、零字面量门禁随全量测试一起跑，任何一处回退都会红。

## 二、年终奖临界区间：从规则表推导，而不是硬编码

### 2.1 现象

全年一次性奖金单独计税时，税率按"奖金 ÷ 12 查按月换算税率表"确定，但**税基是奖金全额**。
在级距边界附近，多发一元可能跳上更高税率档，导致税后到手反而变少——这就是常说的
"多发一元、到手变少"临界区间（业内也称年终奖"盲区"）。

### 2.2 推导

设按月换算表某级距边界（月口径）为 `bₘ`，年口径边界 `b = bₘ × 月份数`（月份数来自规则包，
非日历字面量）。边界左侧级次 `(r₁, q₁)`、右侧级次 `(r₂, q₂)`（`r` 税率、`q` 速算扣除数）。
奖金 `B` 的税后净额 `N(B) = B − (B·r − q)`。

区间左端点为边界本身 `b`；右端点 `B*` = 右侧净额追平左端边界净额 `N(b) = b·(1−r₁) + q₁` 的奖金值：

```
B* = ( b·(1−r₁) + q₁ − q₂ ) / (1 − r₂)
```

陷阱区间 = 开区间 `(b, B*)`：区间内多发奖金，税后反而低于 `b` 处。当 `B* ≤ b` 时该边界无陷阱
（级距边界税额连续，速算扣除数已吸收），自动不产出区间——机制保留，无需特判。

**关键点：端点全部由规则包税率表推导，代码里不写任何端点数值。** 规则表一变（如未来档位调整），
区间自动跟随。

### 2.3 实测定稿：全部 6 个边界都产出区间

一个容易误判的直觉是"只有首区间（36000 附近）有陷阱"。本项目按推导逐边界计算，
在 2019-2026 全部规则包下**6 个级距边界全部产出陷阱区间**（下表以 2024 年度规则为例）：

| 边界（年口径） | 左/右税率 | 左/右速算扣除数 | 陷阱区间 (b, B*) |
|---|---|---|---|
| 36000 | 3% → 10% | 0 → 210 | (36000, 38566.67) |
| 144000 | 10% → 20% | 210 → 1410 | (144000, 160500.00) |
| 300000 | 20% → 25% | 1410 → 2660 | (300000, 318333.33) |
| 420000 | 25% → 30% | 2660 → 4410 | (420000, 447500.00) |
| 660000 | 30% → 35% | 4410 → 7160 | (660000, 706538.46) |
| 960000 | 35% → 45% | 7160 → 15160 | (960000, 1120000.00) |

原因是按月换算表的速算扣除数**不随年口径缩放**（税基用奖金全额），使得每个边界的右净额
都低于左边界净额，故每个边界都存在追平点。这与只算首区间的常见做法不同，是推导而非经验所得的结论。

### 2.4 查表死区（一个必须交代的工程细节）

"商数保留两位小数仅用于定档"引入一个细节：实际跳档点会晚于级距边界数分
（死区宽度 = 月份数 × 申报精度半分）。死区内仍落左级、税后不低于边界锚点。
因此穷举基准与边界扫描一律从**实际跳档点**起断言"区间内到手变少"，恢复点 = 推导右端点的
**申报精度值** `money(B*)`。

在少数边界（如第 3、5 档），`money(B*)` 向下取整后严格小于精确 `B*`，该恢复点仍落在
精确开区间内、被判定为"命中陷阱区间"——这是**正确行为**（该点税后已在申报精度追平锚点），
基准按"与精确上端的相对位置"推导其归属，引擎的开区间语义不变。

### 2.5 双向对账：推导 × 穷举

推导是解析解，穷举是数值验证，两者独立实现、互为对照：

- **解析路径**：上述端点公式，纯 Decimal 循环；
- **穷举路径**：走独立的右级次净额公式 `_local_net`（不调用引擎查表），
  粗扫全区间（1 元步长、采样断言净额非降）+ 恢复窗口逐分细扫，精确命中首个恢复分点。

全逐分穷举 6 个区间约两千七百万步不可行；两段穷举（粗扫 + 窗口细扫）能精确命中首个恢复分点
（净额逐分非降由量化算术保证：`money` 对 `B` 单调、每分原始增量小于半分）。
M4 实测：6/6 区间穷举恢复点 = 推导右端点申报精度值，单次全量基准不足 1 秒。

## 三、依据联动：每个结果数值都能追溯到文号与条款

### 3.1 设计

引擎输出不是裸数值，而是**带依据的 Report 树**：每个数值叶子挂 `ref` 节点
（`{"source": "S61", "clause": "第六条"}`，指向规则包 sources[] 中的文号）。规则包的 `sources[]`
登记每份文件的文号全称、URL、核对状态与核对说明。

前端层用统一渲染函数把 ref 变成人读文本（CLI 与 GUI 共用同一语义，不另起第二套）：

- `render_ref(ref, sources)` → "国家税务总局公告2018年第61号 … 第六条（累计减除费用…）"（依据面板逐条列全文）；
- `short_ref(ref)` → "S61·第六条"（表格行内紧凑引用，完整文号由图例给出）。

### 3.2 覆盖的数值条目

一次完整计算（calc）会产出的依据清单覆盖：

- 减除费用（预扣链与汇算链）——61 号公告第六条；
- 逐月命中的预扣率级次及其速算扣除数——税率表一 + 61 号公告附件预扣率表一（双出处键 `ref`+`ref_qd`）；
- 年度汇算命中的综合所得税率级次——个税法税率表一 + 附件速算扣除数；
- 七项专项附加扣除各自的标准依据（41 号办法 / 国发〔2022〕8号 / 国发〔2023〕13号，逐项挂条款）；
- 年终奖单独计税的税率级次与政策有效期（164号 / 42号 / 30号，按年度挂当期有效文件）；
- 临界区间两侧级次（表机制性推导的出处）。

GUI「依据面板」把这些去重后与来源图例（文号 + URL + 核对状态 + 核对说明）并排渲染；
CLI 则在每张表末尾输出来源图例。**修 bug 凑答案的路被堵死**：真值库 `data/truth/cases.json`
对账时若引擎答案与真值不符，纪律是改引擎而非改真值，且门控保证未核对条目不得生效。

### 3.3 与门控、零字面量的呼应

三条纪律在设计上是同一件事的不同侧面：

1. **零政策字面量**（代码里没有裸数值）→ 强制所有数值都来自规则包；
2. **规则包每条挂 ref + status**（数值必有出处且经核对）→ 保证来源可溯、未经核对不生效；
3. **Report 每个数值挂 ref**（结果必带依据）→ 把可溯源一路传到用户界面。

合起来即"无出处不得入库、未核对不得生效、生效即可溯源"。

## 四、内置基准：把上述设计变成可复跑的硬指标

`incometax benchmark [--year YYYY]` 一条命令跑全四类自洽性检查（纯规则通路、零 API、无随机数、固定输入可复现），
期望值由独立实现路径推导，与引擎**双向对账**（避免"同一代码自己测自己"）：

| 基准 | 方法 | 达标线 | v0.6.0 实测 |
|---|---|---|---|
| 算例回归 | `data/truth` 真值算例 × 引擎输出全字段键集对账 | 通过率 100% | 4/4 ✅ |
| 税率级次临界 | 两张表 96 个有限边界 ±0.01 精确邻域（级次切换/年度表连续/年终奖跳变/引擎通路含商数死区） | 与规则表自洽 100% | 752/752 ✅ |
| 年终奖陷阱区间 | 6 区间：粗扫全区间 + 恢复窗口逐分细扫 + 端点内外 ±0.01 | 穷举恢复点 = 推导端点申报精度值 | 116/116 项检查（6/6 区间）✅ |
| 扣除互斥组合 | 全年度 × 组合矩阵（互斥全档位/分摊上限/重复/非法字段/年度适用 + 有效对照） | 误放行 0 且误拒 0 | 190 违规全拒 / 122 有效全放行 ✅ |

**合计 1184 项检查全过**，单次运行不足 1 秒。GUI 的「内置基准」页复用同一 `run_all()` API，
呈现同一 `BenchmarkReport` 对象——同一份证据，两个入口。

## 五、交付形态与可复现路径

- **核心层零第三方依赖**（stdlib + `decimal.Decimal` 全链路）：税额计算是纯确定性数值问题，
  零依赖使打包最小、CI 稳、审计简单；`decimal` 是为了检出"多发一元"级别的差异——float 尾差会污染临界点判定。
- **两个前端消费同一引擎**：CLI（`incometax` 命令，退出码 0/1/2 锁进测试）与 PySide6 桌面应用
  （`py -m incometax.gui`）。两者的计算编排共用 `engine/pipeline.compute_full_calc`，
  不另起第二套行为。
- **Windows 桌面交付**：PyInstaller onedir 打包，规则包与真值库内嵌进 `sys._MEIPASS/data`
  （数据目录定位顺序：显式 `--data-dir` > `INCOMETAX_DATA_DIR` > 内嵌 > CWD 上溯）。
  构建后断言：dist 无禁区成分（无源码/缓存/测试/计划文档）、内嵌数据与仓库逐文件 sha256 对账；
  冻结态验收：在中立目录调用 exe `--selftest`，验证内嵌数据定位 + calc 全链路 + 内置基准全达标 + GUI 冒烟。

复现步骤：

```bash
py -m pip install -e ".[dev,gui]"
py -m pytest -q                 # 全量测试（含 GUI offscreen、门禁、位级守门、真值对账）
py -X utf8 -m incometax benchmark   # 内置基准，1184 项全达标
py -X utf8 tools/build_package.py --clean-build   # 打包 + 构建后断言
py -X utf8 tools/verify_package.py                # 中立目录冻结态验收
```
